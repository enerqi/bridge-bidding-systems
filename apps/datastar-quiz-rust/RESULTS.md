# Load runs

Measured on **2026-08-28**, on the machine the python numbers in `../datastar-quiz/COMPARISON.md`
and the Go numbers in `../datastar-quiz-golang/RESULTS.md` were measured on: 24 cores, Windows, over
loopback, load generated by `apps/dsquiz-perf/` (locust) on the same box.

The harness is **unchanged**, and it is the same harness the other two columns were driven with — it
reads the mount prefix, the variant query, the question nonce and the candidate count off the page
rather than assuming them, so one client drives all three servers. That is the point: what differs
is the runtime, not the load.

```shell
just dsrs serve-1core                                     # or `just dsrs serve`
DSQUIZ_PERF_HOST=http://127.0.0.1:5070 just dsperf headless 1000 40 200
```

`req/s` in the first two tables is **not** a capacity number — it is set by the scenarios' think time
and by the ~1 s answer choreography. *"Where one core actually saturates"* is where the ceiling is.

---

## Player + filter + cold-visit scenarios

`just dsperf headless <users> 40 200`, all three scenarios mixed.

Three things to read out of that, and one of them is not flattering.

### Memory is the headline

99 MB against Go's 278 MB at the same load, and 53 MB against 171 MB at 400 users — **2.8–3.2×
smaller** for identical work on an identical corpus, against a python worker that is itself smaller
than the Go one. That is what the brief was asking about, and it is not an abstract property of the
runtime; it is four specific decisions, each measurable on its own:

| | go | rust | |
|---|---|---|---|
| one parsed call | 40 bytes | **6 bytes** | `Kind` and `SuitClass` are enums, not `string` |
| the prepared swedish corpus | ~25 MB, tens of thousands of allocations | **0.72 MB, 4 allocations** | one flat arena (`src/flat.rs`) instead of `Vec<Vec<Vec<Bid>>>` |
| one memoised filter hit | 40 bytes (`[]Auction`) | **4 bytes** (a `u32` in a shared `Arc<[u32]>`) | Go's heap profile showed ~15 MB of live memo under this load |
| the brotli encoders | a `sync.Pool`, sized by hand | none | dropped with the response, freed *then* |

The last row is the no-GC part stated plainly. There is no pool here because there is nothing to
amortise: the encoder's pages go back to the allocator at the end of the response rather than
whenever a collector next runs, so the resident set is the working set instead of the working set
plus whatever has not been swept yet. The Go port needed the pool to get from 506 MB to 150 MB; this
one never needed the question asked.

### The CPU is ~12% lower, not 5× lower — and the reason is worth the section below

0.223 cores against 0.253 at 1,000 users. That is a small number and it is the honest one. The
closed-loop table below shows this server doing the same renders **3–8× faster than Go with
compression off**, and the whole of that advantage is spent inside brotli, which both
implementations call at the same quality on the same bytes.

### The aggregate P95 is WORSE than Go's, and it is one route

17 ms against 5 ms. It is not spread across the mix — every route in the table above is within a
millisecond or two of Go's. It is the player scenario's `GET /` alone:

| `GET /` (player scenario, 1 core, 1,000 users) | P50 | P95 | reqs |
|---|---|---|---|
| go | 10 ms | 45 ms | 1,435 |
| rust | 31 ms | 72 ms | 1,185 |

That row is 2.9% of the requests and it drags the aggregate P95 from ~5 ms to 17 ms. It is **not**
service time — the closed-loop probe below serves `GET /` *faster* here than Go does, compressed or
not. It is what happens to the most expensive route when 1,000 users are spawned at 40/s and every
one of them navigates at once. The same scenario's `GET / (cold)` row, which is spread over the run
rather than bunched into the ramp, is P50 2 / P95 20 ms against Go's 2 / 13. So the finding is:
**under a burst of the most expensive route, one tokio worker queues worse than one `GOMAXPROCS=1`
Go process does.** Both recover completely and neither fails a request, but it is a real difference
and it is the only place in this document where Go's numbers are better at the same load.

## Where one core actually saturates

Same method the Go port's ceiling was found with: ramp the same scenarios against a one-worker server
and sample the process's own CPU time (`TotalProcessorTime` over an 80 s steady-state window, so it
is the server's consumption and not a sampler's guess).

| users | **rust cores** | go cores | rust req/s | rust agg P50 | rust agg P95 | rust `/answer` P95 | rust RSS | failures |
|---|---|---|---|---|---|---|---|---|
| 400 | 0.110 | ~0.10 | 83 | 2 ms | 19 ms | 5 ms | 53 MB | 0 |
| 1,000 | 0.223 | 0.253 | 204 | 2 ms | 17 ms | 7 ms | 99 MB | 0 |
| 2,000 | 0.501 | 0.524 | 397 | 3 ms | 43 ms | 31 ms | 204 MB | 0 |
| **4,000** | **0.922** | **0.998 — collapsed** | 710 | **12 ms** | 110 ms | 97 ms | 361 MB | **0** |
| 5,000 | 0.995 | — | 812 | 200 ms | 590 ms | 590 ms | 506 MB | 0 |
| 6,000 | 0.988 | — | 898 | 210 ms | 1,300 ms | 1,100 ms | 589 MB | 1 (0.00%) |

**~4,300 simulated players saturate one core**, against the Go port's ~3,850 — about **13% more
headroom**, which is the same ~12% seen from the other end. The cliff is between 4,000 and 5,000: at
4,000 this server sits at 92% of a core with a **12 ms** P50 and no failures, where Go at 4,000 was
pinned at 99.8% with a 120 ms P50 and the first failures of any run in either document. At 5,000 it
is pinned and the P50 is 200 ms.

Cost per user, which is what makes the extrapolation an extrapolation rather than a guess:

| users | 1,000 | 2,000 | 4,000 |
|---|---|---|---|
| rust milli-cores per user | 0.223 | 0.251 | 0.231 |
| go milli-cores per user | 0.253 | 0.262 | 0.250 (clipped) |

So **~0.235 milli-cores per player, ~1.15 ms of one core per request**, and a ceiling of ~750–800
scenario-shaped requests per second.

The deployable number is lower than the saturation number, and it is the one to size against:

- **≤ 2,000 users** (0.50 cores) — P95 43 ms. Comfortable.
- **4,000** (0.92 cores) — P50 12 ms, P95 110 ms, nothing failing. This is the knee, and it is a
  whole thousand users past where the Go port had already fallen over.
- **5,000+** (1.00 core) — collapsed.

RSS climbs through the ramp (361 MB at 4,000, 589 MB at 6,000) because by then it is dominated by
per-connection buffers for six thousand live sockets, not by anything the app holds. The prepared
corpus is still 0.72 MB per system at every row.

## Per route, head to head — and where the ceiling actually is

A closed-loop probe: no think time, N distinct sessions, one route at a time, **both servers on one
core, alternating in the same run** so nothing drifts between them. 8 s windows, concurrency 4 unless
noted, and each route run twice — once with `Accept-Encoding: br` and once with `identity`.

| route | go, brotli | **rust, brotli** | go, identity | **rust, identity** |
|---|---|---|---|---|
| `GET /` (full page, ~23.4 KB) | 785 | **955** | 1,337 | **10,933** |
| `POST /restart` (full fat morph) | 605 | **809** | 1,499 | **4,806** |
| `GET /filter/preview` (conc 1) | **4,284** | 3,035 | 6,071 | **7,576** |
| `GET /filter/preview` (conc 4) | **6,157** | 3,564 | — | — |
| `GET /filter/preview`, memo MISS | **7,176** | 4,354 | — | — |
| `POST /settings` (204 no-op) | 21,734 | 21,785 | — | — |
| a mixed sweep | **5,235** | 4,194 | — | — |

Read the two right-hand columns first, because they are the finding:

**With compression off, this server is 8.2× Go on a full page and 3.2× on a fat morph.** That is the
askama-into-one-buffer renderer, the flat corpus and the borrowed session lookup, and it is the size
of difference the effort was aimed at. **With compression on it is 1.22× and 1.34×.** Everything
else was spent inside brotli.

Turning that into a cost per request (`1/rps_brotli − 1/rps_identity`):

| | go | rust | compression's share of the request |
|---|---|---|---|
| `GET /` | 526 µs | 956 µs | go 41%, **rust 91%** |
| `POST /restart` | 986 µs | 1,028 µs | go 60%, **rust 83%** |
| `GET /filter/preview` | 68 µs | 198 µs | go 29%, **rust 60%** |

**The `brotli` crate at q5 is slower than `andybalholm/brotli` at q5 — 1.0× to 2.9× depending on the
payload** — and because compression is 60–91% of every response this app sends, that single library
choice decides the per-route ranking. It is the whole explanation for the one row where Go looks
comfortably ahead: `/filter/preview` is 1.25× *faster* here uncompressed (7,576 vs 6,071) and 0.71×
compressed (3,035 vs 4,284). Nothing about the matcher, the session or the renderer is involved.

Two consequences worth knowing before tuning anything else:

- **Moving compression to a reverse proxy multiplies this server's ceiling by 6–11×**, against the
  Go port's ~2×. A deployment behind nginx is doing that anyway (and would then cache the assets
  too). The ~4,300-user ceiling above is a brotli ceiling, not an application one.
- The quality is fixed at **q5, minimum 256 bytes**, because the brief asked for the same compression
  in all three columns and the python's is q5. Dropping to q4 here is the obvious lever and is
  deliberately not pulled, because it would make the comparison a comparison of settings.

*(The Go figures here are lower than the same routes in `../datastar-quiz-golang/RESULTS.md` — 605 vs
794 on `/restart` — because that run had the machine to itself and this one interleaves two servers.
The comparison **within** this table is the valid one.)*

## The measurement that reversed the Go port's fix

The Go port's memory bug was a brotli encoder allocated per SSE response, and its fix was two
changes: pool the encoders, and pin the sliding window to 2^16 = 64 KB, comfortably larger than the
~28 KB fat morph that is the biggest thing this app streams. The window pin was copied here on the
reasoning that it is the same algorithm on the same payloads.

It cost 82% of the throughput. Measured on the real 23,453-byte page, brotli q5:

| window | encode | output |
|---|---|---|
| `lgwin` 16 (64 KB, the Go port's) | 6,078 µs | 5,333 bytes |
| the crate's default | **789 µs** | **5,294 bytes** |

**7.7× the CPU for 0.7% worse compression** — because in this crate `lgwin` also sizes the
metablocks, so a small window does not merely bound the history, it makes the encoder re-scan. End to
end, `POST /restart` served **158 req/s** pinned against **912** with the default, and it presented
as "Rust is mysteriously five times slower than Go at rendering" for as long as it took to bisect.
The one-line change that fixed the Go port's memory would have cost this one most of its ceiling.

Compression ratio is unaffected by the revert and is in line with the others: a full page is 23,453
bytes raw and 5,294 compressed (**4.4×**), against Go's fat patch at 27,709 → 4,935 (5.6×) and the
python's 23.6 KB → 4,069 (5.8×) on their slightly different pages.

## The held-timer scenario

`DSQUIZ_TIMER=stream` gives every open tab an SSE connection pushing a signal patch every 100 ms —
the mode the python side could not carry, and the one axis where the two runtimes differ in kind.
`just dsperf timer-stream 400 20 240` against `--timer stream --threads 1`:

| | go, 1 core | **rust, 1 core** |
|---|---|---|
| users | 400 mixed (timer-holders + players) | 400 mixed |
| held `/timer` streams opened | 669 over 240 s | 671 over 240 s |
| server CPU | — | **0.095 cores** |
| aggregate P50 / P95 | 2 / 6 ms | 3 / 8 ms |
| `POST /answer` P50 / P95 | 1 / 3 ms | 3 / 5 ms |
| answer SSE stream mean | 985 ms | 1,013 ms |
| **RSS mid-run** | 123 MB | **48 MB** |
| failures | 0 | **0** |

Both hold it comfortably; interactive latency alongside several hundred pushed connections is
indistinguishable from the client-interval mode's in either. The difference is again the resident
set — 48 MB against 123 MB for the same 671 streams — and the CPU, which at under a tenth of a core
says the ticking itself is not the cost either way.

*(The first attempt at this run measured nothing: the server was started in the default `client`
timer mode, the route answered 204, and the scenario's own client-mode detection parked every holder.
Seven requests instead of 671. The scenario says so in its log line, which is the only reason it was
caught.)*

`just dsrs bench` — `engine`, `bidfilter` and `corpus` are free of the HTTP stack, so these run with

| a topic (several patterns), 7,627 auctions | 43 ms | 270 µs | **94.3 µs** | 2.9× |
| the same, memo hit | — | 15 µs | **154 ns** | 97× |

The memo-hit row is the arena paying off twice: Go's 15 µs is copying a `[]Auction` out of the cache,
and 154 ns is cloning an `Arc<[u32]>`. It is also the row that never shows up in a load run, because
at that size it is not what the request costs — brotli is.

`prepared heap 0.72 MB` and `one Bid is 6 bytes` are printed by the benchmark itself, so the two
numbers the README claims are re-measured every time it runs.

## Caveats

- Loopback only, and the load generator shares the machine with the server. The 24-core rows in
  particular measure a box where locust has 23 cores to itself.
- `req/s` in the scenario runs is scenario-bound, not server-bound, up to the point the ramp finds.
- The python column is from `../datastar-quiz/COMPARISON.md`, measured on the same machine but not on
  the same day and not interleaved with these runs. The Go column is from
  `../datastar-quiz-golang/RESULTS.md` except where a table says the two were interleaved.
- RSS on Windows is not a like-for-like against a python process's RSS. Between the Go and Rust
  columns it is a fair comparison — same OS, same metric, same load — and the per-object table above
  says where the difference comes from.
- `/answer` percentiles are TTFB in every column (locust stops its clock at the headers on a streamed
  response); the whole-stream mean is reported separately.
- There is no CPU profile of the Rust server to set beside the Go port's pprof output. The
  compression share is derived from the `identity`/`brotli` A/B instead, which is a coarser
  instrument but measures the same thing end to end.
